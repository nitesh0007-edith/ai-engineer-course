Look at this small function. It adds a piece of a document (a "chunk") to a list (a "batch"). It has a bug that has slipped into real, working software many times:

```python
def add_chunk(chunk, batch=[]):     # looks harmless
    batch.append(chunk)
    return batch

print(add_chunk("doc1"))            # ['doc1']
print(add_chunk("doc2"))            # ['doc1', 'doc2']  ← wait, what?
```

The second call should have started a new, empty batch. Instead it still had `"doc1"` inside. Here is why. Python builds that `[]` only **one time** — when it first reads the function, not each time you call it. So every call that uses the default shares the *same* list. In an AI pipeline, this bug can quietly mix one user's documents with another user's. And it never shows an error, so it is easy to miss.

Python is a great language, but it has a few traps like this one. This chapter teaches the small set of Python habits that keep these traps away from your data. You will use these habits in almost every file you write for the rest of the course.

## The intuition

Here is the main idea to remember: **most of an AI system is a small amount of Python that connects to outside services and moves messy data around.** You call a model, and sometimes it is too slow and times out. You read its answer, and sometimes the answer is broken. You process a group of documents, and sometimes one of them is a 400-page PDF. The model itself is not your code. Your code is everything *around* the model.

This tells us which parts of Python matter most. Not fancy, advanced features — the plain, important habits that make this connecting code safe to trust. They do five jobs:

- **Describe your data** clearly, so you catch bugs early — <Term id="type-hints">type hints</Term> and <Term id="dataclass">dataclasses</Term>.
- **Change and stream your data** without using too much memory — comprehensions and <Term id="generator">generators</Term>.
- **Add the same extra behaviour to many functions** — like retrying, timing, and cleanup — with <Term id="decorator">decorators</Term> and <Term id="context-manager">context managers</Term>.
- **Survive errors and show what happened** — error handling and logging.
- **Organise it** so the project is easy to find your way around — project layout.

None of this is advanced. But it is the difference between code that works once in a notebook and code that keeps working when real users use it.

## Describe your data: type hints and dataclasses

A **type hint** annotates what a value is meant to be:

```python
def embed(text: str, model: str = "small") -> list[float]:
    ...
```

Python does not check these hints while it runs. If you call `embed(42)` with a number instead of text, Python still runs it. So why write them? Because other tools read them for you. Your code editor uses them to autocomplete and to warn you about typos. A checker called `mypy` reads them to find type mistakes before you share your code. And later, a library called Pydantic reads these same hints to check what a model gives back and to describe the tools a model can use. So hints are a base that much of the later work stands on.

<Callout type="watch-out">
Python does not force type hints while the program runs. They are more like notes that other tools can read and use. When you truly need to be sure a value has the right type at run time — and you always do for anything coming back from a model — you must check it yourself with a tool like Pydantic (Layer 4). Hints catch mistakes you can see in the code. Checking at run time catches the bad values that arrive from outside.
</Callout>

A **dataclass** is the normal way to group related values together — like settings, a record, or a result — without writing all the setup code by hand:

```python
from dataclasses import dataclass, field

@dataclass
class ChunkConfig:
    size: int = 200
    overlap: int = 20
    sources: list[str] = field(default_factory=list)   # note: NOT sources=[]

cfg = ChunkConfig(size=100, sources=["a.pdf", "b.pdf"])
print(cfg)
# ChunkConfig(size=100, overlap=20, sources=['a.pdf', 'b.pdf'])
```

You get a lot for free: a setup step (`__init__`) that knows the types, a clear printout (the `repr`), and a way to compare two of them. Now look at `field(default_factory=list)`. This is the safe way to give a dataclass an empty-list default. It builds a *new* list for each object instead of sharing one — so it avoids the shared-list bug from the start of the chapter.

## Transform and stream: comprehensions and generators

A **comprehension** builds a collection in one readable expression — the common "filter then map" in a single line:

```python
docs = ["  hello  ", "", "  world ", "   "]
cleaned = [d.strip() for d in docs if d.strip()]   # keep non-empty, strip each
print(cleaned)                                     # ['hello', 'world']
```

Read it out loud: *"take each `d` in `docs`, remove the spaces, and keep it only if something is left."* It does the same job as a longer four-line loop. It looks strange at first, but after a little practice it is easier to read, not harder.

A **generator** looks like a function, but it uses `yield` to give back one value at a time and then pause, instead of building the whole list at once. This is not just a small detail. It is how you *stream* data — handle it piece by piece as it arrives.

<Figure id="00-01.1" label="LAZY VS EAGER" caption="— a list computes and holds all values at once; a generator yields one on demand and keeps only the current one live. For a stream of LLM tokens or a dataset too big for memory, only the generator is viable.">
  <GeneratorStream />
</Figure>

```python
def stream_tokens(text):
    for word in text.split():
        yield word              # produce one, then pause until asked for the next

for i, tok in enumerate(stream_tokens("streaming feels faster than waiting")):
    print(f"token {i}: {tok}")
# token 0: streaming
# token 1: feels
# ...
```

This is the same idea as reading a model's answer as it comes in, word by word, instead of waiting for the full answer. It is also how you read a file with a million rows without loading all million rows into memory at once. There is one catch: a generator can only be used **once**. If you loop over it a second time, you get nothing, because it does not keep the old values to give them again.

## Wrap behaviour: decorators and context managers

In an AI system, many functions need the *same* extra behaviour. For example, every call to a model provider should retry if it fails, stop after a timeout, and measure how long it took. Copying that code around every call leads to bugs. A **decorator** fixes this. It wraps a function and adds behaviour around it, without changing the function's own code.

<Figure id="00-01.2" label="A DECORATOR WRAPS A CALL" caption="— @retry receives the call, invokes the real call_api, and on error loops back to try again; on success the result passes out. The wrapped function knows nothing about retries.">
  <DecoratorOnion />
</Figure>

```python
import functools

def retry(times):
    def decorator(fn):
        @functools.wraps(fn)                 # preserve fn's name, docstring
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    print(f"attempt {attempt} failed: {e}")
            raise RuntimeError(f"{fn.__name__} failed after {times} attempts")
        return wrapper
    return decorator

@retry(times=3)
def call_api():
    ...
```

The `@functools.wraps` line matters. Without it, the name of your function (`call_api.__name__`) becomes `"wrapper"` instead of `"call_api"`. Then every log message and error trace that prints the function name shows the wrong name. You will run this whole example yourself in the next section.

A **context manager** makes sure cleanup always happens. Anything you open — a file, a network connection, a timer — must be closed again *even if the code in the middle fails*. The `with` block does this for you:

```python
from contextlib import contextmanager
import time

@contextmanager
def timer(label):
    start = time.perf_counter()
    try:
        yield                                    # the body of the `with` runs here
    finally:
        print(f"{label}: {(time.perf_counter() - start) * 1000:.1f} ms")

with timer("retrieval"):
    results = search(query)      # even if this raises, the timer still prints
```

The key part is `finally`. The cleanup runs on the way out, no matter what happens. In a real app, this is what closes your database connections and network clients. Without it, these stay open and pile up until the program runs out of resources and crashes.

## Survive and reveal failure: errors and logging

Calls to models and networks fail often. The rule is simple: **only catch the errors you know how to handle, name each one, and never hide all errors at once.**

```python
try:
    response = call_model(prompt)
except TimeoutError:
    response = call_model(prompt, model="backup")   # a failure you can handle
except ValidationError as e:
    logger.warning("bad model output: %s", e)
    raise                                           # can't handle — re-raise
```

The common mistake is a bare `except:` (or an `except Exception:` that does nothing). It hides the very bug you need to see. It even blocks `Ctrl-C`, so you cannot stop the program by hand. Catch only the errors you have a plan for, and let the others show themselves.

**Logging** is how a running program tells you what it did. Use the `logging` module instead of `print`. It gives you message levels (like info or warning), timestamps, and a way to turn messages on or off without changing your code:

```python
import logging
logger = logging.getLogger("pipeline")

logger.info("processed %d documents from %s", count, source)   # lazy %-formatting
```

Two habits to build from day one. First, pass the values as extra arguments (`"... %d ...", count`) instead of building the full string with an f-string. This way, Python only builds the message if it will really be shown. Second, **never log secrets or personal user data** — no API keys, and no full prompts that might hold personal information (this is often called PII, "personally identifiable information"). Logs often get sent to systems you do not control. Logging becomes very important later (Layer 5), and building the habit now is free.

## Organise it: project layout

A script grows into a service. A predictable layout keeps it navigable:

```text
myservice/
├── pyproject.toml          # dependencies, tool config (next chapter)
├── README.md
├── src/
│   └── myservice/
│       ├── __init__.py
│       ├── config.py       # dataclasses / settings
│       ├── clients.py      # model & API clients (context managers)
│       ├── pipeline.py     # core logic (generators, comprehensions)
│       └── logging.py      # logging setup
└── tests/
    └── test_pipeline.py
```

Putting your code under `src/myservice/` instead of at the top of the project is on purpose. It makes you import your package the same way other people will, so you avoid the "it works on my computer" bugs that come from importing local files by accident. Each file has one clear job. This may feel like too much for a small 200-line project, but it helps a lot as soon as the project grows past that.

## A worked example

Here is what real pipeline code looks like, with several of these habits working together. Read it by following what happens to one bad input.

```python
from dataclasses import dataclass
import logging

logger = logging.getLogger("ingest")

@dataclass
class Doc:
    id: str
    text: str

def clean(docs):
    """Yield cleaned docs one at a time; skip and log the broken ones."""
    for d in docs:
        try:
            text = d.text.strip()
            if not text:
                raise ValueError("empty after strip")
            yield Doc(id=d.id, text=text)
        except (AttributeError, ValueError) as e:
            logger.warning("skipping doc %s: %s", getattr(d, "id", "?"), e)
```

Follow a group where the second document has `text=None`. The generator gives back the first clean `Doc` right away, so the next step can start using it now. On the second document, `None.strip()` fails with an `AttributeError`. The `except` catches it, writes `skipping doc ...` to the log, and the loop moves on to the third. One broken record does not crash the whole run, does not disappear without a trace, and does not block the good records behind it. That is the goal: **clear data, one-at-a-time streaming, errors kept under control, and an honest log line.**

## Production reality

Open any real AI codebase and you will see these habits everywhere. They are not just style — the system depends on them:

- **Type hints are everywhere.** Pydantic uses them to check every input and output of a model while the code runs. A type hint on a function becomes the exact shape (a JSON Schema) that the model must fill in. In production this is not optional — it is the wall that stops broken model output from spreading through the rest of the system.
- **Every call to a provider is wrapped with a decorator** — retry, timeout, and often a "circuit breaker" (it stops calling a service that keeps failing). A plain `client.generate(...)` with no wrapper will bring your app down the first time the provider has a bad minute. You will build these in Layer 4.
- **Answers are streamed with generators.** If words start appearing after 200 milliseconds, users feel it is fast, even if the full answer takes 8 seconds. If nothing appears for 8 seconds and then it all shows at once, it feels broken. Generators are what let you show the answer as it arrives.
- **Good logs are the eyes of the system.** When an agent does the wrong thing in production, the log of what it read, what it called, and what it returned is often the only way to work out why. Teams that skip logging have to debug blind.

These habits also have costs, and it is fair to name them. Type hints take extra effort, and they can get hard to read for very complex types. Putting too many decorators on one function — say, five stacked on top of each other — makes the flow hard to follow. Use a decorator when the behaviour is *shared and repeated*, not for a one-off case. Generators save memory but can only run once, which is fine until you forget and loop over one twice. These trade-offs are small, but it is better to know they exist than to copy patterns blindly.
